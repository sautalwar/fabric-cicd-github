1. Architecture Overview

Problem: Power BI report deployment is manual — developers build .pbix files in Power BI Desktop, then manually upload them to Fabric workspaces via the browser. No version control, no audit trail, no environment promotion.

Solution: Two automated deployment paths triggered by Git push, orchestrated via GitHub Actions:

Path A Direct PBIX Upload

Push .pbix to reports/
↓
GitHub Actions (ubuntu-latest)
↓
Power BI REST API POST /imports
↓
Report live in workspace ✓

Path B Convert + Git Sync

Push .pbix to pbix-source/
↓
pbi-tools extracts → PBIP text files
↓
Auto-commit to pbip-output/
↓
Fabric Git Sync API (updateFromGit)
↓
Workspace syncs from repo ✓

4. Path A — Direct PBIX Upload (deploy-pbix.yml)

📤

deploy-pbix.yml

Path A

File: .github/workflows/deploy-pbix.yml

Runner: ubuntu-latest

Trigger: Push to main, dev, or test branches when files in reports/**/*.pbix change, or manual workflow_dispatch

Step-by-Step Workflow Execution

  1. Checkout repository with Git LFS
    Uses actions/checkout@v4 with lfs: true to pull the actual .pbix binary files (not just LFS pointers). fetch-depth: 2 allows comparing with previous commit.
  2. Determine target environment
    Checks if triggered by workflow_dispatch (uses input), push to test branch, or defaults to dev. Outputs the environment name for subsequent steps.
  3. Authenticate to Microsoft Entra ID
    Calls POST /oauth2/v2.0/token with client credentials. Scope: https://analysis.windows.net/powerbi/api/.default. Masks the token in logs with ::add-mask::.
  4. Find PBIX files to deploy
    For push events: runs git diff --name-only HEAD~1 HEAD -- 'reports/**/*.pbix' to find only changed files. For workflow_dispatch: finds ALL .pbix in reports/.
  5. Deploy each PBIX file
    Loops through each file, calling scripts/import-pbix.sh with the file path, workspace ID (from environment-specific secret), and access token. Tracks success/failure counts.
  6. Write deployment summary
    Outputs a GitHub Step Summary with environment, actor, commit SHA, and list of deployed files. Always runs (even on failure).

5. Import Script (import-pbix.sh)

📜

scripts/import-pbix.sh

Path A

Purpose: Uploads a single .pbix file to a Power BI workspace via REST API and polls until import completes.

Usage: import-pbix.sh <pbix-file-path> <workspace-id> <access-token>

Step-by-Step Script Execution

  1. Parse arguments & validate
    Accepts 3 positional args or env vars (PBIX_FILE_PATH, POWERBI_WORKSPACE_ID, ACCESS_TOKEN). Validates file exists on disk.
  2. URL-encode the display name
    Strips .pbix extension, then URL-encodes the filename using jq -sRr @uri. Handles spaces, special characters (e.g., "Sales Report Q1" → "Sales%20Report%20Q1").
  3. Upload via POST /imports
    Calls:
    POST /v1.0/myorg/groups/{workspaceId}/imports?datasetDisplayName={name}&nameConflict=CreateOrOverwrite
    Sends file as multipart/form-data. Extracts importId from JSON response.
  4. Poll import status
    Calls GET /imports/{importId} every 10 seconds. Checks importState field:
    • Succeeded → extract Dataset ID + Report ID, exit 0
    • Failed → print errors, exit 1
    • Anything else → keep polling (up to 60 polls = 10 minutes)
  5. Output results
    On success, prints Dataset ID and Report ID. If running in GitHub Actions (detects GITHUB_OUTPUT env var), writes them as step outputs for downstream use.

Exit Codes

CodeMeaning
0✅ Import succeeded — Dataset & Report IDs available
1❌ Failure — API error or import failed
2⏰ Timeout — import didn't complete in 10 minutes

API Endpoints Used

Base URL: https://api.powerbi.com/v1.0/myorg

Upload:  POST /groups/{workspaceId}/imports
              ?datasetDisplayName={encodedName}
              &nameConflict=CreateOrOverwrite

6. Path B — Convert & Deploy (path-b-convert-deploy.yml)

🔄

path-b-convert-deploy.yml

Path B

File: .github/workflows/path-b-convert-deploy.yml

Trigger: Push to main when files in pbix-source/**/*.pbix change, or manual workflow_dispatch

Jobs: 2 sequential jobs — convert (Windows) → sync-to-fabric (Ubuntu)

Job 1: Convert (windows-latest)

  1. Checkout with LFS & full history
    Uses fetch-depth: 0 for full Git history (needed for commit/push). Token: GITHUB_TOKEN (allows push back).
  2. Download pbi-tools.core
    Queries GitHub API for the latest pbi-tools release. Downloads the win-x64 zip, extracts it, and adds the exe to PATH. This is a standalone .NET tool — no Power BI Desktop needed.
  3. Convert PBIX → PBIP
    For each .pbix in pbix-source/: runs pbi-tools.core extract {file} -outPath pbip-output/{name}/. This produces text-based JSON/TMDL files that are diffable and reviewable in PRs.
  4. Auto-commit converted files
    Configures Git as github-actions[bot], stages pbip-output/, commits with message containing [skip ci] (prevents infinite loop), and pushes to main.

Job 2: Sync to Fabric (ubuntu-latest)

  1. Authenticate to Entra ID
    Same client credentials flow as Path A, but with scope https://api.fabric.microsoft.com/.default (Fabric API instead of Power BI API).
  2. Get latest commit hash
    Queries GitHub API for the latest commit on main (which includes the auto-commit from Job 1). This hash is passed to Fabric so it knows what to sync.
  3. Trigger Fabric Git Sync
    Calls:
    POST /v1/workspaces/{id}/git/updateFromGit
    Body includes the commit hash and conflict resolution policy (PreferRemote = repo wins over workspace). Polls the long-running operation until complete (up to 10 minutes).
  4. Write sync summary
    Outputs workspace ID, commit hash, actor, and status to GitHub Step Summary.

Why Windows Runner?

pbi-tools.core is a .NET application that uses Windows-specific libraries to parse the PBIX file format (which is essentially a compressed package containing Analysis Services model definitions). It cannot run on Linux.

Fabric Git Sync API

POST https://api.fabric.microsoft.com/v1/workspaces/{workspaceId}/git/updateFromGit

Headers:
  Authorization: Bearer {fabric-token}
  Content-Type: application/json

Body:
{
  "remoteCommitHash": "{sha}",
  "conflictResolution": {
    "conflictResolutionType": "Workspace",
    "conflictResolutionPolicy": "PreferRemote"
  },
  "options": {
    "allowOverrideItems": true
  }
}

Git LFS Configuration

The .gitattributes file ensures *.pbix files are stored with Git Large File Storage:

*.pbix filter=lfs diff=lfs merge=lfs -text

This prevents binary .pbix files (which can be 50–500MB) from bloating the Git history. LFS stores them efficiently as pointers with the actual content in LFS storage.

8. End-to-End Flow (Start to Finish)

Path A: Developer Deploys a Report Directly

  1. Developer builds report in Power BI Desktop
    Creates or modifies a .pbix file locally using Power BI Desktop application.
  2. Saves .pbix into reports/ folder
    Copies the file to the reports/ directory in their local clone. Git LFS tracks it.
  3. Pushes to main branch
    git add reports/Sales_Report.pbix && git commit -m "Update sales report" && git push
  4. GitHub detects path match → triggers deploy-pbix.yml
    The workflow trigger filter paths: ['reports/**/*.pbix'] fires the workflow on the ubuntu runner.
  5. Workflow authenticates to Entra ID
    Uses secrets AZURE_TENANT_ID + AZURE_CLIENT_ID + AZURE_CLIENT_SECRET to get an OAuth token for Power BI API.
  6. Workflow identifies changed .pbix files
    git diff HEAD~1 HEAD finds only the files that changed in this push.
  7. Calls import-pbix.sh for each file
    Script uploads via POST /imports with nameConflict=CreateOrOverwrite, then polls every 10 seconds.
  8. Report appears in Fabric workspace
    Within 1–5 minutes, the report and its dataset are live in the DEV workspace. Dataset ID and Report ID are logged in the workflow output.

Path B: Developer Wants Diffable/Reviewable Deployment

  1. Developer builds report in Power BI Desktop
    Same as Path A — creates or modifies a .pbix file locally.
  2. Saves .pbix into pbix-source/ folder
    Uses the pbix-source/ directory instead of reports/.
  3. Pushes to main branch
    git push — triggers the Path B workflow.
  4. GitHub Actions spins up a Windows runner
    Required because pbi-tools.core is a Windows .NET application that parses PBIX internals.
  5. pbi-tools.core extracts PBIX → PBIP
    Converts the binary .pbix into text-based PBIP format (JSON model definitions, TMDL measures, Power Query M expressions). These are human-readable and diffable.
  6. Converted files auto-committed to pbip-output/
    Git commit as github-actions[bot] with [skip ci] in the message to prevent recursive workflow triggers.
  7. Second job authenticates to Fabric API
    Uses same SPN credentials but with Fabric scope (api.fabric.microsoft.com).
  8. Calls Fabric Git Sync API
    POST /workspaces/{id}/git/updateFromGit tells the workspace to pull latest from the repo. Conflict resolution: repo wins.
  9. Fabric workspace reflects the changes
    Reports, datasets, and semantic models in the workspace update to match the PBIP files in the repo. Full audit trail in Git history.
